## 3. 詰めていないこと（GQA にまとめてほしい問い）

各問いの推奨は sandbox-8d の案である。持ち主は自分で確かめ直してから問うこと。

### 問 1. 規則の正本をどこに置くか

いま正本は、Sandbox の作業ブランチの検討書 9 章にある。各チームが普段見る場所ではない。どこに置くかは外部との約束に近いので、オーナーの裁定が要る。

| 選択肢 | 中身 |
|:---|:---|
| a（推奨） | gr-sw-maker の `process-rules/review-standards-ja.md`（NDD レビュー基準書）の隣に、新しい文書として置く。どのチームも NDD の基準書を引いているので、そこから参照できる |
| b | grsmd-qa の SKILL に節として足す。GQA を書く全セッションが読む |
| c | 各チームの開発規則に、それぞれ写しを置く（写しの食い違いの心配がある） |

### 問 2. GRSMD と GRWB の今の規則との突き合わせ

sandbox-8d が食い違いを調べたのは、gr-scheduler の `docs/development-rules/06-pending-decisions.md` だけである（06 の A と C のうち UI に当たるものは、裁定が要る側へ移る）。GRSMD の公開リポジトリには、裁定の扱いを書いた開発規則が見当たらなかった。GRWB の規則は読んでいない。

- 持ち主が、GRSMD と GRWB の今の規則（CLAUDE.md、記憶、SKILL など）を読み、9 章と食い違う所を一覧にする。
- 食い違いのうち、9 章の方針で決まるものは問わずに直す。決まらないものだけ問う。

### 問 3. 安全策 T1〜T5 を各チームでどう回すか

T1（負債の週報）が数える基準線・暫定の印・既知の赤・関数の大きさ・マジックナンバーは、gr-scheduler の仕組みを前提に書いた。GRSMD と GRWB に同じ数え手があるかは確かめていない。

| 選択肢 | 中身 |
|:---|:---|
| a（推奨） | 各チームの PMO が、自分のチームで数えられる物だけで T1 の表を作る。数え手の無い物は「数え手なし」と書き、T4（負債の定義表）の問いに回す |
| b | 全チームに gr-scheduler と同じ数え手を先に作る |

### 問 4. 取り込みを終えたと誰が判定し、どこに記録するか

| 選択肢 | 中身 |
|:---|:---|
| a（推奨） | 各チームの BOSS が、自分の規則に取り込んだ commit を持ち主に知らせる。持ち主が全チーム分をそろえて、オーナーに 1 回だけ報告する |
| b | オーナーが各チームの報告を直接受ける |

### 問 5. まだ決まっていない値

- **週間の使用量の測り方**: 決まっていない。測れるまでは、各 BOSS が使用量の表示を見て判断し、残りが 20% を切ったらオーナーに問う（検討書 8 章）。測り方の候補は、Claude のアプリの使用量の表示、Claude Code の `/usage`、セッションの記録に残る使用制限のイベント。
- **T3 の覆った率の線**: 10% は例の値で、オーナーは裁定していない。最初の T3 の集計を出すときに、値も問う。
